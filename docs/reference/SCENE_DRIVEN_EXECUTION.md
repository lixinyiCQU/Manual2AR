# 现场驱动的 U7 执行计划

2026-11-11。对应第二轮“底座已安装，仅安装支架”编译出单步但无法进入 AR 的修正。新增开关 `stateful_planning`，界面名称 **现场驱动执行规划**；旧基线默认全关，旧候选及历史成绩不改写。全部优化预设现在包含11项。

## 入口

重新打开本工作树构建的教学系统，模块二 → 提问并生成 AR 指导 → 实验设置，单独启用“现场驱动执行规划”，或启用全部优化。必须重新生成候选；继续旧任务仍运行其冻结的旧方法。

本模式的链路：

`问题/照片检索 → 官方完整任务编译 → 逐节点能力绑定 → 官方参考辅助的现场条件对齐 → 执行建议 → 用户确认进入 AR → 当前画面重新评估 → 操作/观察/核验 → 更新会话状态 → 下一节点`

与旧模式相比，scene_alignment 同时开启时不重复在编译前调用旧对齐器，而是在完整任务生成后使用新条件级对齐；该调用包含部件对齐。这是新架构的组合效果，不是逐项复现旧十开关。

## 三份数据分开保存

| 数据 | 来源及内容 | 能否授权完成 |
| --- | --- | --- |
| 完整任务 | 只给编译器所选官方章节、完整动作/条件，用户进度不进入编译上下文 | 不能，定义要检查什么 |
| 现场状态 | 当前照片+官方参考对应部件、每个生成条件的 satisfied/unsatisfied/unknown、用户原话声明 | 不能，是待核验观察 |
| 执行状态 | 当前会话、步骤、帧、照片、核验结果和人工条件确认 | 当前条件核验通过后才能推进 |

用户完成声明保存在 `user_claims`，quote须为输入的连续原话，关联任务state_id；没有官方citation字段。编译器的标题和applicability不再包含用户“已完成”的描述，避免把用户进度挂到Wiki出处上。

初次粗Scene仅用于检索。完整任务生成后，再提供本任务官方图片及原文来辨认灰色料盘支架底座、白色可拆卸支架和当前连接关系，不用“白色塑料件”摘要直接决定进度。新增对齐的条件必须覆盖完整任务，明确结论须有当前照片证据框，manual/sensor渠道必须unknown，低置信度转unknown；照片SHA、部件及观察点ID均校验。资料图片解释对象，不能作为用户已完成的现场证据。

## 执行模式

- `operate`：评估认为可见条件尚未满足。先定位/识别，再指导操作；米制动画仍需标定与已授权作用点。
- `check`：可能已安装。隐藏安装动画，先核验当前可见状态，不重新要求安装。
- `observe`：遮挡、矛盾或证据不清楚。提示补拍连接处并重新评估，不启动安装动画。
- `complete`：本会话的全部任务节点已核验完成。

用户声称已装但照片条件未满足时，保留冲突提示，不把声明写成完成。支架已装的画面应走现状核验；仅底座已装则先核验底座，不必为底座动画配置位置，再指导支架操作。底座隐藏机械紧固仍须按候选条件人工核实。

初始照片只生成建议，进入 AR 后不继承任何完成标记；摄像头送入当前画面后自动再评估一次。每次推进到新节点也重新评估，不照搬最初照片的支架位置。评估失败可点击“重新评估现场”重试，不自动循环消耗模型调用。

“核验现状”无需先看到定位标记或设置动画作用点；这是单图视觉检查，不提供三维定位。若需要显示三维安装动画，旧的相机标定、固定标记、空间授权检查全部保留。

## 编译与执行接口

新增模块：

- `guidance/scene_planning.py`：TaskScene/ConditionState/UserClaim，官方参考辅助对齐，生成执行建议。
- `guidance/stateful_spatial.py`：独立会话状态、当前节点调度、重新评估、检查与推进；复用原识别/定位及当前单图核验接口。
- Unity `SpatialExecution.cs`：当前画面评估、操作/检查模式、按计划推进，不通过旧固定底座门控回退。

服务契约 `wiki-to-ar-v1.4`。新模式运行契约 `compiled-spatial-v3`；旧候选继续 `compiled-spatial-v2`。`Candidate.execution_plan` 显示各节点建议，`Reply/Check/Session.execution` 返回实际会话状态，含当前state_id/action_id、mode、reason、完成与剩余state_id、是否需重新评估。

新增 `POST /api/guidance/pipeline/candidates/{id}/spatial/sessions/{session}/assess`，请求与verify相同：action_id、target_id、client_frame_id。返回身份绑定的当前现场对齐及execution。评估与核验互斥；步骤/目标改变、核验推进或图片超时后的旧评估不能覆盖当前状态。

绑定从“必须恰好base+slide”改为逐节点支持检查（仅新模式）。允许现有能力的单个节点或按顺序的两节点；不补写人工U7步骤。当前模板仍只支持 `holder.base` / `holder.slide` 各至多一次，其他能力或重复能力实例需要扩展动作实例适配器，不能宣称支持任意操作程序。

若输入是仅剩滑入的片段而首节点仍有前置条件，不因没有base节点就无条件解锁：这些前置要求作为独立观察/人工检查门控，核验前置只解锁当前操作，不标记滑入已完成。

## 不变的约束

- 最终核验只送当前现场图；规划对齐可以看参考，但不能替代最终核验。人工确认不能绕过失败的视觉条件。
- 顺序门控依据本会话当前任务节点；未来节点不可跳过。旧epoch、照片/目标、请求token及超时检查保留。
- 推进状态在会话内独立保存，退出后重新进入需重新评估和核验；不从旧照片或旧人工教学进度恢复已完成。
- 生成的任务、初始现场对齐和执行建议均冻结哈希；编辑后不可批准。相机标定仍可复用，空间配置仍按候选隔离。

## 数据与验证

生成目录新增 `scene-state.json`、`task-scene.*`、`execution-plan.json`；AR会话目录有每次assessment输入/图片角色/原返回、`execution-state.json`，事件 `execution.assessed/updated`。调用数继续纳入原calls日志，Token/费用不估算。

`tests/backend/test_stateful_pipeline.py` 检查四类现场、只读初始观察、用户声明冲突、单节点前置门控、失败不放行及篡改拒绝。Unity受控验证检查无实物相机的评估→底座现状核验→人工机械条件→后续支架现状核验；不据此声称真实相机/VLM精度。

本轮实际验证结果及模型失败记录另见仓库外 `runs/u7-pipeline/stateful-validation/`。真实照片下生成条件本身是否完整、部件框是否准确仍需人工评分；新增架构不将模型自评当Ground Truth。

- Windows Unity 构建及受控端到端验证通过：`validation-spatial-20261111-111702`。覆盖当前画面评估、底座检查、人工条件确认及支架检查；多帧门控仍要求不同近期帧。

## 核验可执行性契约（2026-11-11 修订）

动作绑定与核验渠道分开校验。`binding/result.json` 新增 `verification_contract`（manual2ar-verification-v1）和 `issues`；候选API透传这两项，失败信息包含状态ID及具体修订要求。

| 条件渠道 | 执行方式 | 完成门控 |
| --- | --- | --- |
| vision | 当前照片核验；开启多帧时保持多帧检查 | 全部可见条件通过 |
| manual | 显示原条件，用户明确逐项确认 | 照片/现场评估不产生人工完成证据 |
| vision + manual | 先视觉，再人工确认 | 视觉失败或不确定时禁止人工绕过 |
| sensor | 当前没有传感器证据适配器 | 明确拒绝并要求接入；不隐式改成人工 |
| 空条件 | 无验收依据 | 拒绝，禁止空列表自动完成 |

纯人工步骤可绑定已有动作，不要求人为补造一个视觉条件；现场计划进入check，用户实际操作或核实后确认。其单帧仅保留会话上下文身份，不调用SceneCheck，也不要求三张照片证明非视觉事实。现有照片/步骤/epoch/确认有效期检查仍生效。

编译及接入校验拒绝把“机械紧固/需人工确认”等混在vision条件中。语义审查明确要求保留有依据的可见外观，另设人工条件；但不会通过复制人工U7来补齐模型遗漏，也不添加资料未支持的卡扣要求。

旧候选冻结保留原结果。本次修复仅影响重新生成的任务，适用于全部开关组合；基线运行正确性不能作为可关闭的消融项。

本次渠道修复验证：后端全量 398 项通过；新增/关联现场执行测试 16 项通过，涵盖纯人工不调用视觉模型、人工确认前不推进、多帧开关不阻塞纯人工、混合视觉失败不可绕过、未知渠道/空条件拒绝和混合条件诊断。交付与后端已更新。历史失败候选只读审计保存在 `stateful-validation/verification-contract-historical-audit.json`，未修改原记录。此次未重跑真实模型、实体相机或GPU；沿用现有前端确认界面。
