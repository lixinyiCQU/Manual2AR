# Manual2AR 交接审计

审计日期：2026-11-12。对象：`Manual2AR-U7-Pipeline` 当前工作树及其启动、构建、资源和实验依赖。审计使用 ponytail 与 ponytail-audit：先读真实调用链，再报告有触发场景的问题；整理阶段保留已有开发进度。

## 这个仓库做什么

系统把设备官方操作资料、用户目标和现场照片接到任务规划、条件核验与 AR 展示。当前可演示的是 Bambu Lab A1 mini 的 U7 两步安装；模块二也保留原开箱、首次打印、进料和退料教材。自动编译、人工审核、不同版本的研究管线继续保留，但部分入口在演示菜单隐藏。

本次按“单用户本地研究与演示、多个 Agent 使用各自独立工作树”审查。公网、多租户和多进程部署不在当前验收范围。重点追踪了来源与资源装载、U7 会话创建、照片观察、人工确认、进度推进、Unity 展示以及 Windows 打包启动；没有把逐文件阅读全部历史组件说成完成了全面形式验证。

## 必须修复

### 1. 构建验证目录可误删另一个真实 Unity 工程

**状态：已修复并验证，记录见文末。**

- **这是什么：** `tools/build/validate_desktop.py` 接收外部验证目录，将三个 Unity 工程目录重新复制进去。
- **具体问题：** 审计时只拒绝当前仓库及其子目录。接手者若把另一个工作树或归档中的 Unity 源工程传给 `--project`，程序会删除其中的 `Assets`、`Packages`、`ProjectSettings`，再复制当前工程；未跟踪资源可能无法恢复。原问题位于该文件约 27–33 行。
- **最小修复：** 只允许空目录或具有工具专有标记的验证目录，其他现存目录直接拒绝；对子目录路径和符号链接同样核对，先完成检查再删除。用现存文件保护场景验证拒绝行为。
- **不修的后果：** 在交接后的首次构建或多 Agent 操作中覆盖另一份开发成果。

### 2. U7 写盘失败可能锁住会话，或让返回错误与实际进度不一致

**状态：已修复并验证，记录见文末。**

- **这是什么：** `apps/backend/src/manual2ar/modules/guidance/u7_demo.py` 为照片、人工确认与会话事件保存输入和执行快照，再向前端返回结果。
- **具体问题：** 原照片路径先把 `row.busy` 设为真，再在 `try/finally` 外创建目录、写入照片；权限错误或磁盘不足可使 busy 一直不释放。照片提交与人工确认原来先替换内存进度，再写接受记录或事件；后续写盘失败时，前端收到失败，但后台已经推进。原问题集中在 `photo()` 和 `manual()`；启动记录同样需要检查失败回滚。
- **最小修复：** 将全部可能失败的写盘放入释放 busy 的保护范围；用准备后的副本构造并持久化记录，成功后才发布内存状态。失败时保留旧进度，不产生虚假的“状态未改变”收据，并允许下一次重试。用注入写盘失败检查状态、busy 和后续恢复。
- **不修的后果：** 正常演示遇到一次存储故障后无法继续，或者用户以为未确认但系统已推进，破坏核验闭环和记录可信度。

### 3. Windows 交付依赖原机器路径，不能直接搬到同事电脑

**状态：已修复并验证，记录见文末。**

- **这是什么：** `tools/build/spatial_delivery.py` 写出 `backend.launch.json`，`deploy/windows/Start-Backend.ps1` 据此寻找 WSL 后端；应用本机配置还引用仓库外数据。
- **具体问题：** 原启动描述保存构建机器的绝对工作树路径。接收方换用户名、目录或 WSL 发行版后，启动器在所有发行版中仍查原路径，直接报源码不存在。仅发送 EXE 或仅复制 Git 代码还会漏掉离线 Wiki、现场证据和 Demo 素材。原定位点为 `spatial_delivery.py` 的 `export_backend_launcher()`、`Start-Backend.ps1` 约 15–18 行。
- **最小修复：** 交接目录提供可检查的布局、配置模板和重定位入口，用接收方路径与地址生成本机配置及启动描述；凭据由接收方单独填写。原交付程序和历史构建证明作为原始件保留，迁移产生的配置需独立注明，不能手改旧证明冒充原构建。
- **不修的后果：** 源码和数据虽然完整，接收方仍无法启动，或者误用另一个工作树的数据和后端。

## 应后续修复

### 4. 失联 Demo 会话没有回收，达到 64 个后拒绝新演示

**状态：保留为后续工作；本轮不把它写成已解决。**

- **这是什么：** 前端 `U7DemoView.cs` 创建会话后保存 ID，退出时删除已知会话；后台 `u7_demo.py` 限制最多 64 个活动会话。
- **具体问题：** 创建请求已在后台成功、前端尚未收到 ID 时退出窗口，会中止请求并丢弃迟到响应。前端不知道 ID，无法删除后台会话；崩溃或强制关闭客户端也可能留下会话。后台没有失效回收，积累达到上限后拒绝创建。参考 `U7DemoView.Generate()/Request()/Finish()` 和 `U7Demo.start()/close()`。
- **最小修复：** 增加有限、可验证的失效会话回收，或让客户端预分配会话 ID，使创建中的会话也可关闭。增加创建响应丢失与异常退出后的恢复测试，保留原历史记录。
- **不修的后果：** 多次中断后需要重启自己负责的后端才能继续演示；不得通过删除实验记录来“清理”会话。

### 5. 离线文章一次渲染失败后，同一进程不会重新排队

**状态：保留为后续工作；本轮不把它写成已解决。**

- **这是什么：** `apps/backend/src/manual2ar/knowledge/wiki.py` 使用后台渲染任务把离线文章变为客户端可显示页面。
- **具体问题：** `render()` 只有任务不存在时才排队；`_render()` 将失败保留为 `failed`。如果首次缺少 Chromium 或渲染进程超时，修复环境后再次点击同一页面仍只返回旧失败，直到重启或清除该任务内存。参考约 172–209 行。
- **最小修复：** 提供明确的失败重试路径，在锁内将 failed 任务重新排队；不让前端轮询自动触发无限重试。测试一次失败后人工重试成功。
- **不修的后果：** 环境已经修复，官方文章仍打不开，接收方容易把缓存状态当成原始资料损坏。当前可在确认无其他工作后重启自己负责的后端恢复。

## 整理取舍

本轮没有仅凭文件名、行数或隐藏菜单就删除业务代码。

- **隐藏研究模块保留。** `BaselineReviewView`、`OfficialCompileView`、`WikiToArView` 仍有研究入口、后端接口和 `tests/unity/WikiPipelineValidation.cs` 的直接调用，承载人工审核、自动编译与方法对照。Demo 简化菜单不等于这些代码已无用。
- **GT 旧版本保留。** `baseline/ground_truth/u7/v1/` 内候选、审核、状态验证和视觉协议版本记录了定义如何收敛，是复查任务语义和复现实验的依据。当前运行入口应指向明确版本，不将历史候选混成最新规范。
- **实验原始件保留。** 自动编译成功与失败、模型原始回复、现场照片、人工审核标签、源码快照及完整性清单不能作为调试垃圾删除。受控 Demo 预设观察须继续标为演示，并与研究评价分开。
- **可重建缓存单独说明。** Python 字节码、虚拟环境和 Unity Library 不作为任务完成证据；离线文章派生缓存与保留的运行缓存应按清单交接。是否随包带走与是否能删除是两个决定，不能用“缓存”一词概括全部实验资源。
- **最小重构围绕交接故障。** 优先修复构建目录保护、状态与记录提交顺序、路径迁移入口及文档入口，不在交接时重写已验证的教学和 AR 链路。未证实重复或无调用的代码不做清理承诺。

## 结论

仓库已有可交接的演示闭环、研究接口和实验来源，上述构建目录保护、持久化一致性及迁移配置已完成受控验证。保留失联会话回收与文章失败重试为明确后续项；接手者先复现稳定演示，再按需要继续真实视觉和跨任务研究。
