# U7 真实相机试验与修复（2026-11-16）

本轮直接操作真实后端，使用 USB Camera 拍摄现场、调用现有 qwen3.8-flash 视觉链路，并由操作者实际安装支架及确认方向、紧固。没有使用预设观察替代模型输出。当前物理场景已安装支架。

## 结果与发现

| 阶段 | 观察结果及系统行为 | 耗时 |
| --- | --- | --- |
| 安装前的新拍照片 | 底座位置、两颗螺丝及外观通过；支架尚未连接；等待底座人工核实 | 20.55 秒 |
| 用户确认底座方向与紧固 | 底座完成，进入滑入支架；AR数据匹配本步，动画不改变完成状态 | 无新增模型调用 |
| 用户滑入后重新拍摄 | 支架可见检查通过，但底座被报告为身份不明，原会话退回未知 | 13.13 秒 |
| 修复后同图对照 | 底座被报告为遮挡，沿用之前核实记录，等待支架方向人工确认 | 7.60 秒 |
| 用户确认支架方向，再拍一张新照片 | 两步保持完成，没有再次退回底座 | 8.82 秒 |

真实采集最初被 Windows“相机”应用占用；关闭其预览后取得新帧。所有采集失败、原始照片和模型输出都保留。

问题不是状态机把“未知”直接放行。安装后整图模型把立柱误框为底座；局部身份核对正确拒绝了这个定位，却没有将底座识别为被已装支架遮挡。GT 本来包含“底座会被装好的支架遮住”的观察边界，实际传给模型的上下文却只选了操作节点的要求，漏掉任务策略中的这些来源原文。

## 做了什么修改

1. 将已审核的任务策略原文加入粗查和局部复核上下文，保持任务操作范围不变。
2. 明确区分“已辨认的物体遮挡目标区域”和“目标或搜索区域身份不明”。两种情况的当前视觉事实都仍是未知；没有修改 GT、检查条件、身份核对或状态沿用规则。
3. 沿用历史视觉证据时，界面摘要明确写“底座沿用本会话已核实记录（当前有遮挡）”。不会声称当前照片看到了隐藏螺丝。

最终视觉、状态和 U7 宿主专项回归共126项通过。另以保存的真实观察做软件回放：新会话没有历史底座证据时仍请求核实，人工确认不能覆盖未知视觉条件。

## 比较分支与统计边界

原HTTP会话的失败没有被删除、改判或回滚。候选试验使用已有的合法检查点恢复能力，在独立目录中从“底座已核实”的历史前缀继续。它复用原会话ID、revision和帧序号，必须同时查看 `branch_id` 与 manifest 哈希；不能把它误认作原服务器失败会话的连续成功执行。

本轮共4次观察、3份不同图像字节、2种物理配置、6次真实模型HTTP调用，provider报告合计21,819 token；未调用GPU。一次同图前后对照和一次新拍复查仅说明这次工程问题得到了修正，不构成视觉准确率、泛化率或统计改进证明。实际人工确认不是独立的逐视觉条件标注。所有本轮演示和候选仍排除正式研究评价。

## AR 与标定检查

真实画面为960×540。按 Unity 现有的4:3居中裁剪得到720×540，与保存的相机采集配置签名匹配；没有把16:9图像直接拉伸后套用标定。操作者确认标记与打印机相对位置未改变。两张照片的标记重投影误差约0.296和0.304像素，保存的底座作用点投影落在底座区域附近。

这只是几何一致性检查。原工作坐标标记为 printed_reference/illustrative_only，滑入位置仍可能由底座参考点推导。本轮没有操作Unity前端进行实体渲染或测量毫米级偏差，不能称实机AR精度已通过。没有改写已有相机、锚点、工作坐标或动作标定文件。
